## 0. The problem, and which reference to follow

A Mech and MeDIC disagree on what the source of truth is. **In a Mech it is the record.** There is
one YAML file per entity. Agents draft, people review in PRs, and every change is logged. **In MeDIC
it is the build.** Products are gitignored and regenerated byte-identically from regulator
snapshots, and only the `mappings/` decision stores are edited by hand. A literal migration
("agents edit records") would give up I-2 determinism and the claim the release rests on: every
published id walks back to a string a regulator published. **We do not do that.**

mechmaker settles which reference to follow. It is Monarch's own Mech template. It offers
`collection: monarch` and `collection: xmech` ("CultureBotAI fleet, claw-governed") as separate
choices, and it ships claw's `mech_shared.yaml` and `history.yaml` byte-identical *(trial: md5
`3cf80648…` and `3742bc20…`, equal to claw's canonical copies)*. So **mechmaker, not the claw
`MECH_STANDARD`, is the contract for MeDIC.** The claw standard is useful background on what holds
across mature Mechs. Its Tier 1.12 (claw fleet membership) does not apply to a Monarch Mech.

mechmaker's conversion model also fits MeDIC's situation: *"Your existing knowledge base stays
where it is. It becomes a source for the new one. Facts copied from it carry a quote of where they
came from … What it never recorded is marked in each record as work to do."* MeDIC's pipeline
already does what the `convert-knowledge-base` skill asks of a conversion script:

| `convert-knowledge-base` rule | MeDIC equivalent |
|---|---|
| Quote what you copy, reference pinned to a fixed version | `SourceAssertion` spans + `regulatory_document_url` + `data/source_manifest.json` fingerprints |
| Look up, never guess; unmapped keeps its text + `CURATION_TODO` | Two-stage deterministic grounding; `sssom:NoTermFound` rows |
| Write the gaps down | `polarity_unverified`, `AssertionFlag`s, coverage gaps |
| Skip loudly | Fail-loud ingest; no silent fallbacks (SPEC §9) |
| License is a hard stop | `LICENSING.md`, `LABEL_SAB_DECISIONS` allowlist (MedDRA, WHO ICD-10 refused) |

**The one real mismatch:** mechmaker's `convert` helper **never overwrites a record** *(trial:
`convert.py` reports existing records as "left alone")*. It is built for a one-shot conversion.
MeDIC is a living source that is rebuilt every release. So the plan is: **MeDIC becomes a Mech
in place, built on the mechmaker template. Its pipeline is a conversion script with a sync mode
that rewrites the sections it owns and never touches the sections curators own.**

## 0b. Pros and cons

Published copy (with the roadmap drawing):
https://claude.ai/code/artifact/38c03b6c-df65-407e-b37e-0b9a5840b90a

**Gains.**
- **Reviewable changes per drug.** Today's products are gitignored monoliths. Review, not any
  diff, found the approval-date smear (2,194 edges) and the MedDRA leak (104 strings) (#46).
- **A curation surface.** Today there are 0 manual SSSOM rows against 12,252 unresolved literals,
  and no extraction-correction store (#20, #21, #14, #23).
- **Quotes verified by construction.** `add-evidence` and `qc-full` prevent a repeat of the 155/164
  fabricated research citations (#44).
- **Closed validation** of every record (#40, #41).
- **Session-level history** and human sign-off per record (`REVIEWED` requires a human event).
- **One definition of green** (`qc.py`); a record browser, docs, 9 skills, optional agent workflows.
- **Visibility:** a mechregistry entry, a shared vocabulary with DisMech, `provides_to` DisMech
  treatments.

**Costs.**
- **The two models pull in opposite directions.** Agent-edited records versus a deterministic
  build. Mitigated by one writer per section, enforced (D3).
- **The sync mode does not exist yet.** mechmaker's `convert` never overwrites, so we build it,
  then upstream it.
- **Licensing exposure** from verbatim regulator text committed to the repo all the time. Mitigated
  by capped spans, regulatory documents kept out of `references_cache/`, and #52 resolved first
  (D4).
- **Capping spans weakens I-8 as written** ("replayable from the record alone"). Restate it as
  record + committed stores + source manifest.
- **Bulk sync PRs are not line-reviewable.** The PR human gate holds mainly for curated sections;
  say so in the registry entry.
- **One-time restructuring:** package renames, schema reconciliation, 14 colliding files.
  **Ongoing:** template-update conflicts.
- **Two artefacts for consumers** (records + products). Products become concatenations of the
  records, with unchanged paths.
- **Shape mismatches** (filename churn, DRON-only drugs, PDF quote checks); **optics** ("AI-curated"
  vs regulatory provenance); **opportunity cost** against v2.0.0. That cost is partly offset:
  #40, #51 and #52 are owed anyway.

**Options compared.**

| Option | Diffs | Curation | Determinism | Verdict |
|---|---|---|---|---|
| Status quo + adopt pieces (history, qc.py, reference validation) | no | partial | yes | fallback if D4 stalls |
| **Generated Mech in place** | yes | yes | yes | **recommended** |
| Fully agent-curated Mech | yes | yes | no | rejected (I-2, I-8) |
| New repo, MeDIC as source | new repo | yes | yes | rejected (two sources of truth) |

## 1. Decisions

### D1: Topology → **in place, on the template** (not a new repo)

| Option | For | Against |
|---|---|---|
| **A. In place**, template applied to this repo (recommended) | One source of truth. Products, exports and the KGX that consumers use stay where they are. No cross-repo sync | One-time collision work (§3) |
| B. New repo from mechmaker; MeDIC becomes its source | Matches mechmaker's documented conversion path; clean template | **Two sources of truth for the same regulatory claim.** `convert` never overwrites, so every MeDIC release would need a cross-repo refresh, which is the D3 problem moved across a repo boundary. Downstream (EveryCure) consumes MeDIC products, not the Mech |
| C. Port pieces by hand, no copier lineage | No collisions | Loses `just update-template`. mechmaker is changing fast (example runs dated 2026-09-30), so a hand port goes stale |

### D2: Record unit → **one record per drug**, class `DrugRecord`, in `data/drugs/`

- Regulatory documents (SPL, EPAR, package insert) are per drug. Each
  `(drug, disease, relationship)` pair belongs to exactly one record, so I-13 noisy-OR aggregation
  stays inside one file. About 4,300 records.
- **Class name `DrugRecord`, not `Drug`.** The template's `record_class` becomes a new `tree_root`.
  MeDIC already has a `Drug` class, so `Drug` would collide *(trial: answering `record_class: Drug`
  generated a second `Drug` class in a second `medic.yaml`)*.
- **`records_dir: data/drugs`** (the template default). It does not collide with the per-source
  `kb/drugs/<source>/` intermediates, so the `kb/` layout stays as it is.
- **Filenames follow the template rule:** stem = `slugify(name)`, enforced by `rule_errors`
  *(trial)*. `id` is the CHEBI CURIE. Cost: a ChEBI label change renames the file and moves its
  `history/records/<slug>/` directory. Measure how often labels change between ChEBI releases
  before accepting this. The fallback is overriding `record_path` to key on the id.
- **Identity root `CHEBI:24431` (chemical entity).** Drugs that normalize only to `DRON:` have no
  CHEBI id. Either mint `medic:` ids for them (the template's documented path) or leave them out
  until #27 builds drug normalization. Count them before deciding.
- **Diseases are not records.** The disease list mirrors `everycure/disease-list`. It stays a
  reference product, with `hands_off_to: dismech` in the registry.
- **Research associations move into the drug record** (`research:` section). Only 9 verified rows
  exist (#44), so the move is cheap now.

### D3: Who writes what → **sections have exactly one writer**

| Section | Writer | How curation changes it |
|---|---|---|
| `id`, `name`, `identity`, `approvals`, `atc`, `features` | pipeline (sync) | `mappings/` stores (existing) |
| `indications`, `contraindications` | pipeline (sync) | `mappings/` + a new extraction-correction store (#21) |
| `research` | curators / research workflow | directly, through `just add-evidence` |
| `discussions` (mech_shared) | curators/agents; the pipeline may seed `CURATION_TODO`s | directly |
| `status`, `curation_history` | sync writer + curators | append-only events |

- **Sync writer:** a `medic.records.sync` built on the template's `write_validated_record` and
  `append_curation_event`. It regenerates pipeline-owned sections, carries curator-owned sections
  over unchanged, and appends one `EDIT` event only where a record's pipeline sections actually
  changed. It writes **one** batch `history/` record per build (`kind: other`, path = the build
  recipe), as the template's `convert` does.
- **Status:** a pipeline-written record with no open `CURATION_TODO` is `PROPOSED`; one with open
  flags is `DRAFT`. `REVIEWED` needs a human `REVIEW` event. The template enforces this already
  *(trial: `rule_errors`)*. Every MeDIC record starts at `PROPOSED` or `DRAFT`, which is honest.
- **Enforcement:** extend the template's Claude PreToolUse hook (`.claude/hooks/validate_record.py`)
  to refuse agent edits to pipeline-owned sections. The rule is then enforced, not just documented.
- **Upstream:** a sync/refresh mode for corpora generated from a living source is missing from
  mechmaker generally. Propose it there once ours works.

### D4: Licensing → **template's CC BY 4.0, plus MeDIC's passthrough, plus capped spans** (blocker)

The template's `LICENSE-data.md` (CC BY 4.0, *"quoted snippets are short excerpts … the cited
works keep their own licenses"*) matches MeDIC's passthrough. CC0 stays ruled out (`LICENSING.md`).
**But MeDIC's spans are not short excerpts.** `span.text` and step `input_value` are uncapped and
hold whole label sections: 13.5 MB DailyMed, 3.1 MB EMA (attribution required), 0.6 MB PMDA
(attribution plus edit notice required). Committing that into `data/drugs/` would make the
template's licence sentence false. Before the first committed corpus:

- **Cap span text in records** to the quoted claim plus offsets, and keep full sections in the
  gitignored build products. This is #51's cap, now applied for licensing reasons.
- **Do not commit regulatory documents to `references_cache/`.** The template commits fetched
  references *(IngestMech commits its cache)*. That is fine for PubMed abstracts but would
  republish EMA/PMDA documents. Gitignore regulatory entries, or validate spans against MeDIC's
  own source cache instead.
- Resolve **#52** (Russia/China full registers) first. A per-drug corpus republishes them
  record by record.
- Add `data/drugs/` and `history/` to `conf/release_assets.yaml` governance, with `NOTICE.md`.

### D5: Fleet → **mechregistry under `collection: monarch`; no claw fleet**

Confirmed by mechmaker's separate `xmech` choice and by DisMech not being in claw's `fleet.yaml`.
The template's vendored files plus `just update-template` keep 1.3/1.4 true. That replaces the
hand-rolled vendored-sync check from the previous draft of this plan.

### D6: Timing → **after `v2.0.0`**

Phase 1 changes no data, so it can start now. Phase 2 changes the shape of what ships, so it
waits for the release (#55, the #59 branch).

## 3. Applying the template in place: the collisions

The trial copy against this repo's tree. Files that exist in both:

`.claude/settings.json`, `.gitignore`, `.linkml-reference-validator.yaml`, `CONTRIBUTING.md`,
`LICENSE`, `README.md`, `conf/oak_config.yaml`, `docs/index.md`, `justfile`, `mkdocs.yml`,
`pyproject.toml`, `references_cache/.gitkeep`, `src/medic/__init__.py`,
**`src/medic/schema/medic.yaml`**.

**Hidden collisions** the path diff does not show. Template modules would shadow existing
packages:

| Template module | Existing package | Resolution |
|---|---|---|
| `src/medic/validate.py` | `src/medic/validate/` (and `validation/` exists too) | Merge `validate/` into `validation/`, freeing the name |
| `src/medic/research.py` | `src/medic/research/` | Move the template module to `research/deep.py` and fix its imports (note this in `.copier-answers.yml` notes; `update-template` will flag it) |
| `src/medic/export.py` | `src/medic/export/` | Fold the template's records bundle into `export/records.py` |
| `src/medic/schema/medic.yaml` | MeDIC master schema | Template base schema becomes `schema/drug_record.yaml`, imported by `medic.yaml`; its `Term`/`EvidenceItem`/`CurationEvent` reconciled against MeDIC's |
| top-level `research/` | 60+ deep-research markdowns | Template's `research/README.md` + templates join them |

Procedure:
1. Do the package renames first, in their own PR, with no behaviour change.
2. `copier copy --trust --data-file conf/mech-answers.yml --skip <every colliding file>` into
   the repo, then hand-merge each skipped file. MeDIC's `justfile` already imports
   `project.justfile`, so the template's justfile can become `justfile` and import
   `project.justfile`.
3. Keep `.copier-answers.yml` committed so `just update-template` works. Accept that later updates
   will conflict on the merged files. That is the price of option A over option C.

## 4. Phases

### Phase 1: Template plumbing (no data change; can start now)

1. Package renames (§3.1).
2. Apply the template (§3.2). `just qc` becomes the gate, with MeDIC's existing checks added as
   steps. CI runs only `qc.yaml`. The template's workflows already set `persist-credentials: false`
   *(trial: all 5)*; add it to `release.yml` and `claude.yml`, which we keep.
3. Fix **#40** so `kb/` validates closed too.
4. Schema reconciliation: `support`→`supports`, `drug_record.yaml` scaffold with no records yet.

**Gate:** `just qc` green locally and in CI with zero records. Vendored schemas md5-equal to claw.

### Phase 2: The record corpus (after v2.0.0)

1. `DrugRecord` composes the existing `Drug` + `indications`/`contraindications`
   (`IndicationAssociation` where this drug is subject) + `research` + `discussions` +
   `status`/`curation_history`. No new semantics; `product_view.py` stays the read-side accessor.
2. `medic.records.sync` (D3) writes `data/drugs/*.yaml` after merge, with capped spans (D4).
3. Products become concatenations of the records. Paths and classes are contractual (SPEC §2) and
   stay.
4. **Corpus-reproduction gate** in `qc.py`: rebuild from committed `kb/` + `mappings/` + source
   manifest, then diff the pipeline-owned sections of `data/drugs/`. Like today's CI rebuild, this
   reproduces from `kb/` onward. Full source→record reproduction stays `just determinism`, run at
   release.
5. Licensing (D4) lands in the same PR.

**Gate:** empty reproduction diff. Products byte-equal to pre-migration (modulo key order).
`just validate-all` clean over `data/drugs/`.

### Phase 3: Curation

1. Seed `discussions` only where a human decision is pending: `polarity_unverified` /
   `over_extraction` / `wrong_pairing` → `CURATION_TODO` on `indications#<pair>`; #14/#23
   coverage gaps → `KNOWLEDGE_GAP`. **Measure counts first.** A class that yields thousands goes in
   a QC report, not in records.
2. Extraction-correction store (#21): the curation surface for pipeline-owned indication content.
3. Ownership hook (D3) live; skills adapted; research workflow writes `research:` sections via
   `just add-evidence`.
4. Optional agent workflows (review, triage, curation-scanner), off by default, per the template.

**Gate:** one curated fix round-trips. A store edit + a history record + a rebuild gives exactly
the expected record diff. One worked example goes in `docs/explainers/`.

### Phase 4: Evidence validation

1. Regulatory references as `url:` CURIEs **pinned to a document version**: the DailyMed SPL
   version, the EPAR revision. An unpinned URL fails validation every time a regulator revises a
   label. Sometimes that is a useful signal, but it is not a curation error.
2. `just qc-full` runs `linkml-reference-validator` over every record. **Unverified:** whether it
   extracts text from EMA/PMDA PDFs (and Japanese PDFs). Test on 5 records before relying on it.
   If it cannot, MeDIC's own span anchoring against its source cache is the `references` gate for
   regulatory evidence.
3. Research sections: PubMed snippets verified by the validator. This is the stated precondition
   (SPEC §8, #44) for regrowing the research axis.

**Gate:** `just qc-full` green.

### Phase 5: Registry

Fill the generated `registry/medic.md` with the `register-mech` skill: `maturity: seeded`,
`validation: [schema, ontology_terms, references, cross_field, corpus_reproduction]`,
`cross_references` to dismech (`follows_pattern_of`, `provides_to` for treatment sections,
`hands_off_to` for disease mechanisms), and `data_sources` listing each regulator as
`prov:hadPrimarySource` and Mondo/ChEBI/EveryCure as `prov:used`. Count `record_count` from
`data/drugs/` on a stated date. Open the PR to `monarch-initiative/mechregistry` only after Phase
2. `agent_curated: true` is honest only after Phase 3.

## 5. Not adopted

- **Causal mechanism graphs:** `causal_graphs: false`. MeDIC records regulatory claims, not
  mechanisms. Drug mechanism of action would be a new axis with its own source, and arguably
  DisMech's.
- **Claw fleet tooling** (D5).
- MeDIC's own invariants (I-1 … I-15), determinism, KGX/SSSOM exports and `mappings/` stores all
  stay. They become extra `qc.py` steps, not template replacements.

## 6. Risks

- **Template churn.** mechmaker is weeks old. Each `update-template` conflicts on the hand-merged
  files. Budget for it, or pin the template commit and update deliberately.
- **Repo growth.** About 4,300 records plus history. Measure at Phase 2. With spans capped it
  should be far below the 57 MB KGX lesson in `LICENSING.md`.
- **Reproduction boundary.** CI reproduces from `kb/` onward, not from regulators. The registry
  entry must say so.
- **Filename churn** from slug-of-name (D2). Measure before accepting.

## 7. Open questions

1. Sign-off on D1–D4. D1 (in place vs new repo) and D4 (span capping) are the expensive ones to
   reverse.
2. Do contraindications stay a sibling section, or become `indications` with a
   `relationship_type`? The record could unify what the products split.
3. Should we raise the sync mode with mechmaker's maintainers before building it, so it lands
   upstream rather than as a MeDIC fork of `convert.py`?
